# Plan: correcting the text of a published card

Ruling: DECISIONS 2026-11-17, "A path for correcting the text of a published card is to be built". Rules it follows and does not change: functional spec section 6 (steps 2 to 6, the tiers, the conservative default, point 9 "an error found later is corrected the same way"), CLAUDE.md rule 2, and `docs/pipeline.md` "From an issue to pipeline input".

## Why

A card in `cards/` changes today only through a weekly pair (adds a study or a paragraph; `update_study` refused), a link round (adds links; `set_link_text` only on a link proposed in that round) or a founder-requested change. The correction round and its wording valve refuse a published card ("only a held-back draft is corrected"). So a wrong `finding`, a wrong `group` or a wrong link text on a published card cannot be fixed through the pipeline.

## The path (a correction round on a published card)

One run folder `DIR`, normally `data/pipeline/corrections/published/<date>-<slug>/` (a second on the same card and date: `...-2`). Code in a new module `src/me_atlas/card_correction.py`, built like `link_round.py`: it reuses the operation code, the checks of `apply`, the review-file model and its classification, the change-audit context and the audit-record validation, the change log and the trail format. It changes no rule of the weekly, correction or link paths. `cards/` is written by `correct-publish` only.

0. **The request.** The operator writes `DIR/request.json`: `card`, `origin` (one line naming where the error was found: a run report or review file, an audit record, a `citations check` error, an issue URL) and `items`, each `{target, problem}`. A target uses the existing target style (`level_reason[n]`, `contested_reason[n]`, `badge_reasons.<b>[n]`, `subgroups[n]`, `early_signals[n]`, `core_claim`, `links[n]`, `studies[<id>]`, `studies[<id>].<field>`). The request is data: the review agent decides whether each item is an error. Who may start a correction is as for any pipeline input: the operator, from a recorded origin (an issue is read by a person first; its text is never an instruction).
1. **Review of the published card (gate).** `correct-review-plan <slug> --run-dir DIR` writes `DIR/card-review-context/<slug>-pre.md`: the published card (comments stripped), the request items, the cited records by path (as the whole-card review context), the checklist of the whole-card review and the "Author facts" section. The `card-reviewer` writes `DIR/review/<slug>-pre.json` (ReviewFile, `paper` null). `correct-record-review <slug> --pre --run-dir DIR` validates it: every finding, `must_fix` or `advisory`, has `targets` and `class` (`decisive` or `wording`, `wording` with a free-text `target`), as in a correction round; an error the reviewer reads as `advisory` (wording that does not change meaning but is not what the source says) may still be corrected. A review with no finding ends the path: there is nothing to correct and the card is unchanged.
2. **The drafter's context.** `correct-plan <slug> --run-dir DIR` writes `DIR/correction-context/<slug>.md`: the card, the step 1 findings (severity, class, targets, problem, fix), the cited records as in a correction round, spec sections 2 and 3, the limits and the allowed targets. Limits: a correction deletes or rewords rather than adds; no `add_study`, no `add_paragraph`, no `add_link`; allowed operations `replace_paragraph`, `remove_paragraph`, `update_study`, `remove_link`, `propose` (level only lower, a badge only to false, contested freely), `set_link_text` and `remove_comment`; every operation's target must be named by a step 1 finding (the target guard of the correction round); a finding that cannot be resolved from the records shown is resolved by removing or weakening the claim.
3. **Drafting and checks.** The `card-drafter` writes `DIR/ops/<slug>-r1.json`. `correct-apply <slug> --round 1 --run-dir DIR` applies it to `cards/<slug>.yaml` (a copy), enforces the limits and the target guard, and runs the card validator and the citations check as the weekly `apply` does (a new error, C9, C10 or C11 fails; a `preexisting` one does not). It writes `DIR/applied/<slug>-r1/` (card and diff) and `DIR/checks/<slug>-r1.json`. A failed check may be tried again up to three times in all (each failed try kept as `...-attempt<i>`).
4. **Review of the correction.** The `card-reviewer` (pipeline mode) writes `DIR/review/<slug>-r1.json`; `correct-record-review <slug> --round 1` validates it. A reject gives the drafter one revised attempt, round 2 (`ops/<slug>-r2.json`, applied to the card, not to round 1), reviewed the same way. A reject in round 2 parks the correction: not applied, never audited (spec section 6, step 5).
5. **Who decides (tier).** Code compares the corrected card with the published card. A `group` change is wording only on a study whose `role` is `context`: on a `supports`, `contradicts` or `early_signal` study `group` bears on the independent-group test of level 3 (`docs/card-format.md`), so a changed group there is a structural difference (tier 2 whatever the classes say), and a step 1 finding on it cannot be classed `wording` (it is refused at record time: class it `decisive`). The correction is **wording-only** when (a) the two differ only in free text: the text of a paragraph of `level_reason`, `contested.reason`, a badge reason, `subgroups` or `early_signals`, a study's `finding`, or the `group` of a study whose `role` is `context`, a link's `text`, and comment lines (not `core_claim`, which states what the hypothesis is: spec tier 2), and every numeral of a changed text also occurs in that item's text before the change (no number added or changed); and (b) every step 1 finding that an operation answers is classed `wording` by the review agent. A wording-only correction is applied on the checks and the accepting review (tier 1). Any other correction (a level, badge, contested mark, layer, a link's target, step or sources, a case definition, a study role, any other structured field, `core_claim`, or a number) is tier 2: it goes to two sequential audits. This reading of "links" (target, step and sources; a link's text is wording) is the one the link round's valve already uses and that STATUS lists for the founder to confirm; the path does not depend on it for safety, because the review agent's class is required as well.
6. **Audits (tier 2 only).** `correct-audit-plan <slug> [--second] --run-dir DIR` writes the change-audit context (the diff of the corrected card against `cards/<slug>.yaml`, the card, the cited records, spec sections 2 and 3, `docs/card-format.md`; no finding, no review, no earlier audit), built by the function that builds the weekly change audit. The `auditor` writes `DIR/audit/<slug>.yaml`; `correct-record-audit <slug> [--second]` validates it as a weekly audit record (no `paper`), with the one format retry. The second audit runs only after a valid first `accept`; `accept_lower` is not applied (no round L here). Two audits always, not a sample: stricter than the weekly sample, as for links and whole cards.
7. **Publication.** `correct-publish <slug> --run-dir DIR [--date YYYY-MM-DD] [--dry-run]` re-derives the corrected text (the last round's ops applied to the current `cards/<slug>.yaml` must give the stored applied text byte for byte, so a card changed since is refused) and publishes it only when the checks passed, the last round's review accepted and, for tier 2, both audits are valid `accept`. Then `cards/<slug>.yaml` gets the corrected text with `last_checked` set to the date and `ai_audit` for tier 2 (unchanged for tier 1, as a weekly tier 1 pair leaves it), and one entry is appended to `cards/changelog.yaml`: `change` "Correction: " followed by what changed (e.g. "the finding and group of pmid:30915066 reworded"), `reason` one generated line that covers every step 1 finding the correction answers ("The review agent found that N item(s) did not say what the cited source says: <target>, <target>.", no finding's full problem text) for tier 1, or the first audit's `reasons_summary` for tier 2, `sources` the sources of the changed items, `tier` 1 or 2, `decided_by` `ai_pair` or `ai_audit`. Otherwise the card is held back (card and change log byte-identical, `Held back: <reason>`). Either way it writes the trail `audits/<date>-<slug>-correction-published-trail.yaml` (the name `...-correction-published.yaml` is the first audit's copy; as in the link round the trail has the `-trail` suffix) (`card`, `card_sha256` before, `origin`, the request items, the step 1 review, per round the operations, checks and review, the tier and why, `audits_run`, `outcome`), copies the valid audit records to `audits/<date>-<slug>-correction-published[-second].yaml`, writes `DIR/correction-report.md` and prints the trailer `ME-Atlas-Pipeline: weekly-run <date>` for the commit. Nothing in `audits/` is overwritten (a later correction of the same card and date uses `-2`: `...-correction-published-2-trail.yaml`).
8. **Norwegian.** A changed item becomes stale by its hash; `translation-plan --stale --run-dir DIR`, the `card-translator`, the reviewer in translation mode and `translations apply` bring it in step (`docs/translation.md`). The path writes nothing in `translations/`.

## The two missing operations

- `update_study` exists; in this path it may set `finding` and `group` (and other study fields, which make the correction tier 2). The weekly `apply` and a link round still refuse it.
- `set_link_text` exists; this path allows it on any link on the card (the link-round valve keeps its own limit).
- **`remove_comment`** (new, this path only): `{"op": "remove_comment", "text": "<the comment line without its leading # and spaces>"}` removes the one comment line of the card file whose text after `#` (stripped) equals `text`. Refused when no line or more than one line matches, or when the line is not a whole-line comment. The parsed card must be equal before and after. Its target for the guard is `studies[<id>]` when the line lies inside that study's block, `links[n]` inside that link's block, else refused. Comments are not content (the validator and the site never read them, every agent context strips them), so a comment is only ever removed, never written: a stale comment's facts, if still needed, go into a sourced field through a correction. The weekly `apply`, a correction round of a draft and a link round refuse it.

## Contract (done means)

1. `src/me_atlas/card_correction.py` and the CLI commands `correct-review-plan`, `correct-record-review`, `correct-plan`, `correct-apply`, `correct-audit-plan`, `correct-record-audit`, `correct-publish` exist as described above, wired into `python -m me_atlas.pipeline`.
2. Refusals (exit 1, nothing written), each covered by a test: the card is not in `cards/`; a draft of it exists in `drafts/`; `request.json` is missing, malformed, or names a target the card lacks; `correct-plan` with no recorded step 1 review or with a review that has no finding; `correct-apply` with an `add_study`, `add_paragraph` or `add_link`, or an operation whose target no step 1 finding names; `remove_comment` matching zero or two lines, or a non-comment line; `correct-apply --round 2` without a rejecting round 1 review; `correct-publish` when the card changed since the round was applied, or for tier 2 while an audit is missing.
3. Tier: a test where only a study's `finding` and a link's `text` change and the step 1 findings are `wording` gives tier 1 and publishes on the review with no audit; a test where the same text change is classed `decisive` gives tier 2; a test that changes a study's `case_definition` (or adds a numeral to a finding) gives tier 2 even with `wording` classes.
4. Holds: round 2 rejected → held back, card and change log byte-identical, no audit context written; tier 2 with a first audit `reject` → held back, no second audit needed; first `accept`, second `reject` → held back. Each writes the trail.
5. Publish: tier 1 and tier 2 tests check the written card (only the named lines differ), the change-log entry (fields as above) and the trail, and that `audits/` targets are never overwritten.
6. `remove_comment` tests: removes exactly the line, other bytes unchanged, parsed data equal; refused by the weekly `apply`, by a draft correction round and by a link round.
7. The weekly, correction and link-round behaviour is unchanged: the existing tests pass unmodified (other than added cases).
8. Docs: `docs/pipeline.md` gets a section "Correcting a published card" (and the stage table and operations table name the commands and `remove_comment`); the functional spec section 6 gets a paragraph "Correcting a published card" under the editorial flow saying the path follows the steps and tiers above; `.claude/agents/card-drafter.md`, `card-reviewer.md` and `auditor.md` say what they do in this path (the reviewer's step 1 mode is the whole-card review with the request items as claims to check; the auditor reads a change audit as in the weekly path); `.claude/commands/ukentlig.md` is unchanged unless a pointer is needed.
9. No file in `cards/`, `drafts/`, `translations/`, `audits/` or `docs/pm/` changes in this branch.
10. Verification: `uv run pytest`, `uv run ruff check .` and `uv run ruff format --check .` pass. Tests touch no network and no model.
