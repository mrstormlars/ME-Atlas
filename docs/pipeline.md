# Weekly pipeline

How new papers reach the draft cards. Plan: `docs/plan-weekly-pipeline.md`. Code: `src/me_atlas/pipeline.py` (the steps code can do) and `src/me_atlas/operations.py` (what the drafter may change). Rules: functional spec section 6.

If this page and the code disagree, the code is right and this page is a bug.

## How to run it

In a Claude Code session in the repository, type:

```
/ukentlig                          # the last 14 days
/ukentlig --since 2026-10-01       # a longer window
/ukentlig --no-pr                  # everything except pushing and opening the pull request
```

The command (`.claude/commands/ukentlig.md`) drives the stages below. AI work is done by subagents on the subscription (table under "Agents and models"): no API key and no `anthropic` calls. A change is applied only when the mechanical checks passed, the review agent accepted it and, for a tier 2 change, the auditor accepted it (spec section 6). The result is a pull request; the founder merges it as an operational step, without reviewing the content. During the trial period (the first four weekly runs) the founder reads the auditor decisions in the report after the fact; a ruling in `docs/pm/DECISIONS.md` ends it. The first publication of a card (the plan's step 6) is a separate command, `publish-card` (section "First publication" below); until a card is published, a pair is applied to the card file the pipeline works on, which is a draft in `drafts/`.

`log.jsonl` in the run directory records each `prepare`, `apply`, `record-classification` and `record-review` call. The whole directory is gitignored (`data/pipeline/`); the audit records that matter are copied into `audits/` by `pr`, and the consistency count is in the report.

By default each command after `prepare` works on the newest run in `data/pipeline/`: the newest folder whose name is exactly a valid ISO date (`YYYY-MM-DD`) and which holds `papers.json`. A folder with any other name (`2026-11-13-livecheck`, `nb-first-run`) is never chosen by default; if no folder qualifies the command stops with a message naming `--run-dir`, which takes any folder. Options on every command: `--run-dir`, `--pipeline-dir`, `--cards-dir`, `--drafts-dir`, `--cache-dir`, `--spec`, `--translations-dir`, `--audits-dir` (default `audits`). `prepare` also takes `--date` (the name of the run directory, default today) and `--force` (start a run of the same date again).

## What `prepare` selects

The papers in the fetch window (`window_pmids` of the run manifest, cached or not) that no earlier run has processed, minus any that are marked retracted. "Processed" is kept in a ledger, `data/pipeline/processed.json` (gitignored, shared by all runs: PMID to the date of the run). Only `report` writes to it, so a run that is aborted before `report` can be repeated and selects the same papers again. `prepare --reprocess` ignores the ledger. `prepare` prints how many papers it selected and how many it skipped as already processed. Retracted papers are never selected, and a newly retracted paper that a card cites is still flagged whatever the ledger says. A newly retracted paper that a card cites is listed in the report; it is the founder's decision how the card changes (spec section 3: a retracted study is removed from the evidence and the level re-assessed).

### Classifying an explicit list of PMIDs

`prepare --ids PMID [PMID ...]` (or `--ids-file PATH`, one PMID per line, a `pmid:` prefix allowed, blank lines and `#` comments ignored) replaces the fetch window with the given ids. It is mutually exclusive with `--since`. Only the listed ids that are not in the cache are fetched, through the same injected fetch as `pubmed fetch --ids ... --cache-dir ...` (nothing is fetched when all are cached), and `papers.json` holds exactly the listed records whatever their entry date. The ledger and retraction rules are those of a window run: an id already processed is skipped unless `--reprocess`, a retracted record is excluded (`excluded_retracted`) and an id whose record is missing or unreadable is listed in `unreadable_records`. No preprint search is made. `prepare.json` records `"mode": "ids"` and the `ids`; `preprints.searched` is false, and the report header says the papers were given by id (not a fetch window) and that no preprint search was made. Everything after `prepare` is unchanged.

Use it for papers the query does not return. For the 9 "CFS/ME" records found by the recall check (`docs/fetch.md`), take the ids from the `sample_pmids` of the term "CFS/ME" in the newest `data/cache/query-diff/*.json` that has it, put them one per line in a file and run `prepare --ids-file <file>`. They are cached already, so nothing is fetched.

## Preprints

`prepare` (in window mode) also searches Europe PMC for preprints first indexed in the same window (`config/europepmc_preprint_query.txt`; the facts about the API and the cache are in `docs/fetch.md`, "Preprints (Europe PMC)"). The search is a function that tests inject, like the PubMed fetch; a failed search fails `prepare` before anything is written. Each preprint is dropped for the first matching reason, and `prepare.json` lists every drop under `preprints.dropped` (PPR id, DOI, reason and details) with `preprints.counts` (found, dropped per reason, offered):

| Reason | Meaning |
| --- | --- |
| `published` | it has a "Preprint of" link to a PubMed record (the PMID, whether it is in the PubMed cache, and the link's note are listed) |
| `in_pubmed` | its DOI (case-insensitive) is the DOI of a record in this run's PubMed window or in the PubMed cache |
| `superseded` | a higher version, whose PPR id is in the same search, exists |
| `duplicate_doi` | several records share this DOI (case-insensitive); the one with the highest version number, then the highest PPR number, is kept and the others are dropped (judged after `published` and `in_pubmed`; the row names the one kept) |
| `no_doi` | no DOI, so it cannot be cited |
| `processed` | the ledger has its PPR id (unless `--reprocess`) |

Survivors are added to `papers.json` after the PubMed papers: `id` `doi:<doi>`, `pmid` null, `preprint` true, `ppr_id`, `journal` the preprint server, `publication_types` ["Preprint"] and `entry_date` the first index date. Every PubMed paper also has `preprint` (true for a PubMed record with the publication type "Preprint", such as pmid:42996068; that record keeps its PMID and flows as any other paper). The ledger holds a preprint under its PPR id, in the same file; PMIDs come first, in numeric order, so a ledger written before preprints reads unchanged.

A classification names its paper by exactly one of `pmid` or `id` (`doi:<doi>`, for a preprint with no PMID); both, neither, an unknown id, a repeated paper and a missing paper are rejected. A DOI-only preprint that matches a card goes into `matches` as `{slug, id}` (a PubMed pair is `{slug, pmid}`) and is drafted, checked and reviewed like any other pair, with the differences below. A preprint that PubMed also holds is a PubMed paper; its context file says it is a preprint and that it can only be added with `preprint: true` and `role: early_signal`.

**The paper key.** Every file of a pair is named `<slug>-<key>…` (`context/`, `ops/`, `checks/`, `review/`, `applied/`). The key is the PMID digits for a PubMed paper (unchanged) and the PPR id (`PPR<digits>`) for a DOI-only preprint, read from `papers.json`. `context`, `apply` and `record-review` take the paper as `<pmid>`, `pmid:<pmid>`, `doi:<doi>` or the PPR id and resolve it against this run's `papers.json`; a `doi:` or PPR id that is not a DOI-only preprint of this run is an error naming it. In an ops file and a review file the paper is `doi:<doi>`.

**Context for a DOI-only preprint.** Built only from its cached Europe PMC record (`europepmc preprint <doi>` caches it; without it `context` stops and names the DOI and that command): id, Europe PMC id, title, server, year, first index date, version, abstract (HTML tags removed), the preprint rule, and the note that the case definition comes from the abstract or the full text, otherwise `unverified`. Full text goes through `get_fulltext(..., preprint=record)` with the same status notes as for a PubMed paper, and the same case-definition sentence lists when there is text.

**Apply, review, report.** An ops file whose `paper` is `doi:<doi>` is checked like any other (validator including V15, citation check against the cached preprint record: C1, C2, C3, C5, C6); its `add_study` must have `preprint: true`, and every operation in it is tier 2. `record-review` expects `paper: "doi:<doi>"` for that pair. The report links the paper to `https://doi.org/<doi>` with the title from the cached record. Conflict parking and the final card text treat the pair as any other.

A study marked `preprint: true` on a card or draft whose cached preprint record (or this run's search result) has a "Preprint of" link is listed in `prepare.json` under `preprints_published` and in the report under "Preprints on cards with a published version". No operation is written; the founder decides.

**Tier 2.** An operation that adds a study with `preprint: true`, or cites a study marked `preprint: true` (on the card or in the same file) in its sources, is tier 2; so is every operation of an ops file whose paper is a `doi:` preprint (the auditor decides). `apply` counts it in `tiers` and the report lists it under tier 2.

## The context file

`context/<slug>-<pmid>.md` is the only thing the drafter and the reviewer read about the paper. It holds six sections, numbered 1 to 6 with no number repeated: (1) the card as it is now; (2) the inclusion rule (spec section 2); (3) the rubric, the evidence ladder (spec section 3); (4) the paper's PubMed record (or, for a DOI-only preprint, its Europe PMC record) with an `- authors:` line (the record's authors in record order, or `not stated`; the drafter takes the names in `group` only from it) and the abstract; (5) the Europe PMC full text when the paper has open full text, without its reference list; (6) sentences from the full text, in two lists under their own labels: sentences that may name a case definition, and sentences that may exclude people with the illness (an exclusion wording together with ME/CFS, CFS or the illness's full name). The second list tells the reader to check whether ME/CFS itself was what the study excluded. The spec excerpts keep their text, but their headings are one level lower, so the only level-2 headings are the six above. If the spec has no section 2 followed by section 3, `context` stops with a message. "Oxford" in a sentence counts as a case definition only when it is not an affiliation, publisher, place or vendor ("University of Oxford", "Oxford University Press", "Oxford, UK", "Oxford Instruments").

The full text note depends on what Europe PMC gave. The PMC id from the cached PubMed record is passed on, because Europe PMC can lack it for a while. `open_access`: the XML has a real body and is used. `pdf_only`: a PMC record exists (with its id), but its full text is a PDF only and it was not read; nothing is cached. `pmc_no_xml`: a PMC record exists (with its id) and Europe PMC has no full-text XML for it. With no PMC id anywhere the file says there is no open full text. A cached lookup that found no open full text is asked again after 7 days (`LOOKUP_MAX_AGE_DAYS`). No PDF is ever downloaded or parsed. The full text is cut at `FULLTEXT_CHAR_BUDGET` (60,000 characters, a constant in `pipeline.py`); the file says `TRUNCATED` with both numbers when it cuts, and says so when there is no full text. It contains nothing the drafter wrote.

## Operations

The drafter writes a list of operations, not a card (`operations.py`). All keys are checked; an unknown key, an unknown field name, a duplicate study id, a paragraph index out of range or an `add_study` without a case-definition quote for a recognised definition is rejected with a message, and nothing is changed.

| Operation | Tier | What it does |
| --- | --- | --- |
| `add_study` | 1 (2 with `preprint: true`) | Appends a study (all Study fields; the id must be the paper itself). `preprint` is written only when true. |
| `add_paragraph` | 1 (2 if it cites a preprint study) | Appends a sourced paragraph to `level_reason`, `contested.reason`, `badges.*.reason`, `subgroups` or `early_signals`. |
| `replace_paragraph` | 1 (2 if it cites a preprint study) | Replaces paragraph `index` of such a field. `field: core_claim` (`index` 0 only; tier 2, it states what the hypothesis is) is correction rounds and the valve only: its `sources` may only be among those `core_claim` already cites. `apply` in a weekly round refuses it, naming the operation. |
| `propose` | 2 | Sets the level, the contested mark or a badge, with the complete new reason. |
| `update_study` | 1 (2 for a preprint study) | Correction rounds only. Changes fields of the study `id` (`set`, a non-empty map of Study fields; not `id`, not `preprint`). The result must validate as a study and pass the `add_study` case-definition provenance rule. Only the named field lines change. |
| `remove_paragraph` | 1 | Correction rounds only. Removes paragraph `index` of a sourced-text field. Refused on `core_claim`, and when it would leave `level_reason` empty, `contested.reason` empty while the card is contested, or a true badge without a reason. A `subgroups` or `early_signals` list may become `[]`, a false badge's reason `null`. |
| `remove_link` | 2 | Correction rounds only. Removes the link whose target is `to`; an unknown target is rejected. |

`update_study`, `remove_paragraph`, `remove_link` and `add_sentence` are for the correction of a held-back draft (section "Correcting a held-back draft"). `apply` in any other round rejects an ops file that holds one, naming the operation.

**How operations are applied.** As text splices, not through a YAML library, because round-tripping would lose this repository's comments and folded text. Only the lines of the named field are replaced or inserted; every other line stays byte-identical. After each operation the edited text is parsed again and compared with the same change made on the parsed data; any difference stops the run. Limits: a field written in flow style on one line, and CRLF line endings, are refused with a message; comments inside a field that is rewritten (a `propose` reason, one replaced paragraph) are lost, comments elsewhere stay. Adding a paragraph to a reason written as a single sourced text turns it into a list of two paragraphs, keeping the first one's words.

## Checks and the two rounds

`apply` never touches `drafts/`. It applies the operations to a copy, then runs the card validator (`cards validate`) and the citations check (`citations check`) on that copy and writes both results. A citation error that the card already had before the change is marked `preexisting` and does not fail the pair; warnings (C6) never do, with one exception: a new (not `preexisting`) C9 warning (the study's `group` names no author of the record, see `docs/citation-check.md`) fails the pair and counts in `citation_errors`, so a drafter cannot add an author name the record does not support. A "TODO" in the name, a sourced text or a study's `finding` fails the pair through the validator rule V14. `group` stays optional, but when every study already on the card has a `group` and an added study has none, `apply` adds one line to the `warnings` list of the checks record for that study and prints it as `warning: ...`. A warning never changes `passed` or the exit code. It is shown in the report next to the reviewer notes of an accepted pair. The number check C10 (every numeral in free text must be in a cited record, `docs/citation-check.md`) is a warning in `citations check` but an error here, for every applied text (weekly pairs, correction rounds, valve fixes); a C10 problem already on the card is `preexisting` and does not block. The author check C11 (a statement about authors that the cached author lists contradict, `docs/citation-check.md`) is a warning in `citations check` and an error for every applied text in the same way, with the same `preexisting` rule. The author check C11 (a statement about authors that the cached author lists contradict, `docs/citation-check.md`) is a warning in `citations check` and an error for every applied text in the same way, with the same `preexisting` rule. Numbers must come from the cited record. Because the copy sits alone, a link from it to another card (rule M2) is resolved against the card files in `--drafts-dir` and `--cards-dir`; a link to a slug found in neither fails the check.

- A failed check: the drafter gets one retry with the errors. Still failing: the pair is skipped and the report says why.
- A passed check goes to the reviewer. The reviewer reads the context file, the operations and the applied result, never the drafter's reasoning (the operations file has no field for any).
- The reviewer gives every finding a severity. `must_fix`: wrong against the sources, the rubric or the checklist; a TODO or internal note in reader-facing text; a field missing that the card's other studies have; a study outside the card's scope; a missing limit that changes how a reader would read the result. `advisory`: wording that does not change meaning. Any `must_fix` means `reject`; `record-review` refuses an `accept` with a `must_fix` finding. A `reject` with only advisory findings is allowed.
- Reviewer says `reject`: the drafter gets one revised attempt (round 2) with the review. Rejected again, or the second attempt cannot pass the checks: **parking lot**. The change is not applied, is never sent to the auditor (no AI step overrides a review rejection) and is listed under disputes in the report. Never a third round. If round 2 passes the checks with no operations after a rejection in round 1, the drafter has withdrawn the change: the pair is `withdrawn`, not `no_change`, and the report keeps the reviewer's findings and what was proposed in round 1. Nothing is applied for it, and `pr` and `translation-plan` write nothing for it. A review file may carry an optional `not_on_card`, one non-empty line: the reviewer's reason to list the paper in the card header's "Not on the card" list (set when a `must_fix` finding says the study is outside the card's scope or stated exclusions). `record-review` refuses an empty string. The report prints it on its own line for the pair.
- `accept`: a pair with only tier 1 operations goes into the pull request; a pair with a tier 2 operation goes to the auditor first (next section). If two papers that may be applied touch one card, `pr` applies their operations in turn to the draft and validates the combined result. If two accepted papers overwrite the same target (the same `replace_paragraph` field and index, or the same `propose` target), neither is applied and both go to the parking lot; other papers on the card are still applied. A pair the auditor did not accept does not count in this comparison.

## The audit

The `auditor` agent decides every tier 2 change (spec section 6, steps 6 and 7). Code: `build_audit_context`, `validate_audit_record`, `audit_sample` and the gate in `collect_outcomes` in `src/me_atlas/pipeline.py`. Contract decisions D1 to D6 are in `docs/pm/DECISIONS.md` (2026-11-13).

**Who is audited (D1, D2).** Every pair whose final round passed the mechanical checks, was accepted by the reviewer and contains at least one tier 2 operation. A pair with only tier 1 operations is applied on the checks and the review and is not audited. A parked pair (rejected twice, or failed the checks after a rejection) is never sent to the auditor and never applied; the report lists it under disputes. The decision covers the whole operations file: anything but `accept` means none of its operations is applied. A parked pair is never audited even if an audit record accepting it exists: `collect_outcomes` gives it no audit state and `audit-sample` never lists it. The founder may overrule a parked change as a logged correction (`decided_by: founder`); no AI step does.

**`audit-plan <slug> <key>`** writes `audit-context/<slug>-<key>.md`, the only file the auditor reads: (1) the diff of the last round (`changes.diff`), (2) the card as it stands, (3) the cached records of every study the card or the applied card cites (see "Full text for carriers" below; a study with no cached record is named under "Not cached" and cannot be cited), (4) functional spec section 2, (5) section 3, (6) `docs/card-format.md`. It contains nothing the drafter or the reviewer wrote, and no earlier audit. The card in it (section 1 of a whole-card audit, section 2 of a change audit) and the diff have their YAML comments removed: the card is parsed and dumped again (`strip_yaml_comments`), and the diff is built from the comment-free base and applied texts, not read from `changes.diff`. Why: comments in a draft carry earlier drafter and reviewer reasoning and earlier rulings, which the auditor must not see. Parsing drops full-line and trailing comments and keeps a `#` that is part of a value. The dumped card is therefore in a stable form that can differ from the file in line wrapping and quoting; its content is the same. `audit-plan --card <slug> [--out DIR]` does the same for a whole card (the card file takes the diff's place) and writes `<DIR or RUN>/audit-context/<slug>.md`.

**Full text for carriers.** A *carrier* is a study cited in `level_reason`, in `contested.reason` or in the reason of a badge (`carrier_ids`). For a whole-card audit these are the carriers of the card file; for a change audit they are the carriers of the applied card, so an id the change newly cites in `level_reason` is a carrier too. A carrier is given with its full cached text, uncut: the record says "Not truncated (N characters)" and there is no character budget. Every other study is given as title, metadata and abstract only, and its record says "Abstract only (not a carrier of the level, a badge or the contested mark)"; its full text is not loaded, and `record-audit` does not accept a quote from it that is not in its title or abstract. A carrier with no cached full text gets the abstract and the plain statement: "FULL TEXT NOT CACHED: only the abstract is given. A statement on the card that is not in this abstract may stand in the full text; it cannot be checked here." The auditor treats such a statement as unverifiable (not shown to be false) and does not accept it on trust: the record names it as unverifiable for that reason in `would_change`, and the decision stays conservative. A whole-card context can be large (a card with many carriers runs to several hundred thousand characters).

**`record-audit <slug> <key>`** validates `audit/<slug>-<key>.yaml` (`--second`: `...-second.yaml`; `--card <slug> --file PATH [--out DIR]` for a whole card). The record has `card`, `paper` (left out for a whole card), `decision` (`accept`, `reject` or `accept_lower`), `accepted_level` (required for and only for `accept_lower`, 0 to 5 and lower than the proposed level, or the card's level for a whole card), `parts` (a non-empty list of `decision_part`, `rubric` and `evidence`, a list of `source` and `quote`), `reasons_summary` (one line, shown in the report) and `would_change`. It is rejected when: a `source` is not a record in the context file; a `quote` is not found word for word in that source's cached record (title, abstract or full text; the same narrow normalisation as the citation check: Unicode NFKC, whitespace collapsed, curly quotes and dashes read as straight, nothing else); a part has no `rubric`, or its `rubric` is shorter than 20 characters after normalisation or not found word for word in functional spec section 2 or 3 (D5); `accept_lower` has no `accepted_level` or one that is not lower; the decision is unknown; the card or paper differs from the pair.

**Why an `accept_lower` is not checked against the ladder row (a rule that was weighed and not built).** `validate_audit_record` checks that every `rubric` is a verbatim excerpt of spec section 2 or 3, not which excerpt. A stricter rule was considered: an `accept_lower` record must have a part whose `rubric` is in the ladder row of a rung above `accepted_level` and at most the proposed level, or in "What moves a hypothesis up or down", or in the case-definition table. It is not enforced, for three reasons. (1) A lower level can rest on text that is in none of those places: the contested-evidence rule, the badge definitions, the quality factors line or the preprint rule, and a record that cites only those is not shown to be wrong. (2) Both real dry-run records of the first card are `reject`, and the contract allows no rule for `reject`; there is no real `accept_lower` record to test a rule against, so a check could not be shown free of false failures. (3) Matching a quoted clause to a ladder row proves that the text was copied, not that it supports the level, so the rule would give a mechanical look to a judgement that is not mechanical. The second audit of the same card by a fresh auditor (which `publish-card` needs, see below) and the founder's reading of the report are the checks on that judgement. If real `accept_lower` records later show a pattern (for example a lower level argued only from badge text), the rule can be added with a test for each side.

**The redraft after `accept_lower` (round L; E3, E4, E5).** The auditor writes no card text, so a lower level is reached through one new draft. `redraft-plan <slug> <key>` (a whole card: `redraft-plan --card <slug> --audit PATH [--out DIR]`) writes `redraft-context/<slug>-<key>.md` for the `card-drafter`: the card the operations apply to (the applied result of the last round), the first audit's `accepted_level`, `parts` (decision part, rubric clause, evidence) and `would_change` and `reasons_summary`, the cited records as in an audit (carriers in full, the others as abstracts), spec sections 2 and 3, and the limits. It refuses when the first audit is not a valid `accept_lower` (also when the second audit of the pair differs from it) and when any file of a round L already exists, so there is at most one redraft. The drafter writes `ops/<slug>-<key>-rL.json`. **E4:** it may contain only `propose` operations: exactly one on `level` whose `value` equals the auditor's `accepted_level`, plus at most one each on `contested`, `diagnostic_marker` and `explains_pem` (only where the lower level makes the existing value inconsistent); its `paper` is the original paper (a whole-card redraft names no paper: the key is left out). `apply --round L` rejects anything else (`redraft_ops_problems`) before the validator and the citations check run, applies the operations on top of the last applied round (so the added study of round 1 stays) and writes `applied/<slug>-<key>-rL/` with the diff against the card; the gate checks E4 again. The reviewer reviews it as in a normal round (`record-review --round L`; it never sees the audit record). `audit-plan <slug> <key> --round L` builds a fresh audit context from the diff of round L against the card (`audit-context/<slug>-<key>-L.md`; the earlier audit record is not in it, E5) and `record-audit ... --round L` validates `audit/<slug>-<key>-L.yaml` (`--second` for the second run). Round L counts neither as round 1 nor as round 2. A redraft is a level change: it is listed in `audit-sample.json` (`why: redraft_level_change`, `round: L`) and needs a second audit. The change (the operations of the last round followed by the redraft's, with a proposal of the last round dropped when round L proposes the same target again) is applied only when the redraft passed the checks, the reviewer accepted it and both round-L audits say `accept`. Otherwise the card is unchanged and the report lists the pair under "Disputes (card unchanged)" with the reason: `redraft failed checks`, `redraft rejected in review`, `redraft not accepted in audit` (reject, `accept_lower` again, no valid record or a differing second run) or `no redraft recorded`. There is no further round. For a whole card the same files are written (`ops/<slug>-rL.json`, `applied/<slug>-rL/`, `audit/<slug>-L.yaml`; use `--run-dir DIR` or `--out DIR` consistently); `pr` does not apply a whole-card redraft to any card file; `publish-card` does, once, for a card's first publication (section "First publication").

**`audit-sample [--seed S]`** writes `audit-sample.json` (the seed and the pairs): every audited pair with a `propose` on `level`, plus one in five of the other audited pairs (rounded up when there are any), chosen with `random.Random(seed)`. The seed is the run date string unless `--seed` is given (D6). Each sampled pair is audited a second time by a fresh auditor (`audit/<slug>-<key>-second.yaml`). A level change needs the second audit even if `audit-sample.json` is missing.

**The gate (conservative apply).** A pair is applied (`Outcome.applied`) only when: its last round passed the mechanical checks; the reviewer accepted it; and, if it has a tier 2 operation, a valid first record says `accept` and, if the pair is sampled, a valid second record also says `accept`. Not applied, and the card file unchanged: `reject`; `accept_lower` (D3: never applied automatically, because the auditor writes no card text; the report lists the level the auditor accepts); a missing or invalid record (the report says why); a second verdict that differs from the first (counted, and listed as a dispute). A redraft at the lower level is the one round L below.

**Who decides about a retraction.** `prepare` flags a newly retracted paper that a card cites; code does nothing more with it. Removing that study from a card, or changing a level, badge or contested mark because of it, is a card change like any other: it goes through drafting, review and (for a tier 2 change) audit. The founder may overrule the outcome, as a logged correction. The report lists the flag under "Retracted papers cited on cards" and does not decide.

**What `pr` writes (D4).** The applied operations go to the card's base file, as `_base_card` picks it: `cards/<slug>.yaml` when that is the card in use, else `drafts/<slug>.yaml`. For a target in `cards/`, `pr` appends one entry per applied pair to `cards/changelog.yaml` with `decided_by: ai_audit` (audited; `reason` is the `reasons_summary` of the audit that decided it: the round-L audit after an accepted redraft) or `ai_pair` (tier 1 only), and an audited change sets `last_checked` to the run date with `by: ai_audit`; a tier 1 only change leaves `last_checked` as it is. Every valid audit record of the run, rejects included, is copied to `audits/<date>-<slug>-<key>.yaml` (`...-second.yaml` for the second run; the audits of a redraft become `audits/<date>-<slug>-<key>-L.yaml` and `...-L-second.yaml`; a whole-card record in `audit/<slug>.yaml` becomes `audits/<date>-<slug>.yaml`, and `audit/<slug>-L.yaml` becomes `audits/<date>-<slug>-L.yaml`) and staged in the same commit. A commit with only audit records and no card change is possible. Nothing is written to `cards/` until a card is published with `publish-card`.

## First publication (`publish-card`)

A card is born in `drafts/`. It moves to `cards/` once, through two whole-card audits run in sequence, with the command

```
uv run python -m me_atlas.pipeline publish-card <slug> --run-dir DIR [--date YYYY-MM-DD] [--dry-run] [--round C<k>]
```

`DIR` is a folder of its own (not a weekly run) that `audit-plan --card <slug> --out DIR` creates. Setting a card's level on first publication is a level change, so it needs a second audit from a fresh auditor (D6). The audits run in sequence: the second auditor is run only when the first record is valid and does not say `reject`. A new draft's first publication does not yet have the whole-card review gate that a correction round has (below). The sequence for one card:

1. `audit-plan --card <slug> --out DIR` writes `DIR/audit-context/<slug>.md`.
2. The `auditor` agent reads it and writes `DIR/audit/<slug>.yaml`; `record-audit --card <slug> --file DIR/audit/<slug>.yaml --out DIR` validates it. A record that fails is given its one format retry (see "The format retry") before anything else is done.
3. Only when the first record is valid and its decision is not `reject`: a second, fresh `auditor` agent (same context file, no sight of the first record) writes `DIR/audit/<slug>-second.yaml`; `record-audit --card <slug> --file DIR/audit/<slug>-second.yaml --out DIR` validates it. A first `reject` ends the audits: `publish-card` holds the card back without a second audit. (For a whole card `record-audit` validates the file you name; it is the file name, `<slug>-second.yaml`, that `publish-card` reads.)
4. Only when the audits say `accept_lower` (both, with the same `accepted_level`): `redraft-plan --card <slug> --audit DIR/audit/<slug>.yaml --out DIR`, the `card-drafter` agent writes `DIR/ops/<slug>-rL.json`, `apply <slug> DIR/ops/<slug>-rL.json --round L --audit DIR/audit/<slug>.yaml --run-dir DIR`, the `card-reviewer` agent writes `DIR/review/<slug>-rL.json` and `record-review <slug> --round L --run-dir DIR` validates it, `audit-plan --card <slug> --round L --out DIR`, two fresh auditors write `DIR/audit/<slug>-L.yaml` and `DIR/audit/<slug>-L-second.yaml`, each checked with `record-audit --card <slug> --round L --file ... --out DIR`.
5. `publish-card <slug> --run-dir DIR --dry-run` writes `DIR/publication-report.md` and changes nothing else; the same command without `--dry-run` publishes.

**A draft is audited once.** `publish-card` without `--round` and `audit-plan --card <slug>` without `--round` refuse (exit 1, nothing written) when `audits/` already holds a whole-card audit record for the slug, with a message that names `correction-plan` (the unchanged draft is not audited again; see "Correcting a held-back draft"). A whole-card audit record is `audits/<date>-<slug>` followed by exactly one of `-second`, `-L`, `-L-second`, `-C<k>`, `-C<k>-second`, `-invalid`, `-C<k>-invalid` and `.yaml`; the match is exact, so a card whose slug starts with this slug is no match, the `card` field of each matching file must be this slug (a card `foo-second` has a record named like the second audit of `foo`), a matching file that cannot be read or has no `card` field stops the command with a message naming it (it is neither skipped nor counted), and a trail record (`...-C<k>-correction.yaml`) is not an audit record. An existing `audits/` target is reported as never overwritten before this refusal.

**What it decides (`whole_card_outcome`).**

- Both first audits valid and `accept`: `cards/<slug>.yaml` is the draft text byte for byte except the `last_checked` block, which gets the date and `by: ai_audit`; `drafts/<slug>.yaml` is deleted (a draft would win over the card in `card_files`).
- Both `accept_lower` at the same `accepted_level`: published only when the one redraft passed every step: its operations pass `redraft_ops_problems` (E4, checked again here whatever the checks file says), the checks file says `passed`, the review says `accept`, `applied/<slug>-rL/<slug>.yaml` is what applying the operations to the draft gives (re-derived, not trusted), and both round-L audits are valid and say `accept`. The card is then the redraft's text with `last_checked` set as above.
- Anything else holds the card back, with the reason on its own `Held back:` line in the report. Audits run in sequence, so a single record can be a complete outcome: a valid first `reject` with no second record at all (no file, no invalid one) holds the card back with `the first audit decided reject; no second audit was run (sequential audits)`, and a first record that failed validation twice (the format retry used) with no second record holds it back with `the first audit record failed validation twice; no second audit was run`; the final invalid record is then copied to `audits/<date>-<slug>-invalid.yaml` (`-C<k>-invalid` in a correction round; the `.invalid-2.yaml` file byte for byte when it is a whole-card mapping of this slug, else wrapped with its text in `raw_text`), so the trail shows that the draft was audited. A first record that failed once and has no retry recorded (`.invalid-1.yaml` only) makes `publish-card` refuse (exit 1, nothing written), naming the pending retry. When a second record exists anyway, the reason about the two audits does not depend on their order: `both audits decided reject`; `the two audits differ: one decided X, the other Y` for any two valid records with different decisions or accepted levels, where X and Y are the two decisions in alphabetical order (an `accept_lower` is written `accept_lower at level N`); it does not say which audit gave which, so the same pair gives the same text in either order; `one audit decided reject and the other audit record is missing or invalid: <why>`; for a missing or invalid record otherwise `no valid first audit: ...` or `no valid second audit: ...` (both, when neither is valid) (a record that failed validation twice says so, see "The format retry"). Then, for an agreeing `accept_lower`: `no redraft recorded`, `redraft failed checks: ...`, `redraft rejected in review`, `redraft not accepted in audit: ...`. A held-back card leaves `drafts/<slug>.yaml` byte-identical, writes no `cards/<slug>.yaml` and no change-log entry.
- The text to publish must also validate as a card in `cards/` (the card validator including V16); if not, it is held back.

**What it writes.** `DIR/publication-report.md` (also printed): the outcome (published at level N, or held back), the reasons, a table of every difference between the draft and what is published (`level`, `contested`, `diagnostic_marker.value`, `explains_pem.value`; "No difference." when there is none; for a held-back card, what the audits would give) and, for each valid audit, its decision, `reasons_summary` and `would_change`. On publication, one entry appended to `cards/changelog.yaml` (created if missing; earlier entries are not touched): `change` "First publication at level N" plus "; the draft had level M" for each difference, `reason` the `reasons_summary` of the deciding audit (the first round-L audit after a redraft), `sources` the distinct evidence sources of that audit's parts, `tier: 2`, `decided_by: ai_audit`. Every valid audit record in `DIR/audit/` for the card, rejects and held-back cards included, is copied to `audits/<date>-<slug>.yaml`, `...-second.yaml`, `...-L.yaml` and `...-L-second.yaml` (and, as above, a first record that failed twice, as `...-invalid.yaml`); an existing file there is never overwritten (the command stops and writes nothing).

**Refusals and the dry run.** The command stops with exit 1, writing nothing, when `cards/<slug>.yaml` already exists, when `drafts/<slug>.yaml` does not, when `--run-dir` is missing, when an `audits/` target already exists, when the first audit record failed validation once and its format retry is not recorded, or when `audits/` already holds a whole-card audit record for the slug (above). `--dry-run` writes only the report. A decision to hold a card back is not an error: the exit code is 0 and the report says so. The command does not commit. It prints the line `ME-Atlas-Pipeline: weekly-run <date>`, which the commit that adds the files must carry as a trailer for `content-paths` (see "The content-path check"). The code is `whole_card_outcome` and `run_publish_card` in `src/me_atlas/pipeline.py`; the tests are in `tests/test_publish_card.py`.

## Correcting a held-back draft

A held-back draft (`drafts/<slug>.yaml` exists, `cards/<slug>.yaml` does not, and `audits/` holds a whole-card audit record of the slug) is not audited again unchanged. It gets at most one correction round, `C1` (`MAX_CORRECTION_ROUNDS = 1` in `pipeline.py`; `REOPENED_ROUNDS` gives `small-fibre-neuropathy` and, since DECISIONS 2026-11-15/16, `mast-cell-activation`, `impaired-energy-production-after-exertion`, `brain-and-brainstem-mri-changes`, `orthostatic-intolerance-cerebral-blood-flow`, `hpa-axis-cortisol` and `herpesvirus-reactivation` a round `C2` too, and `oxidative-nitrosative-stress` a round `C3`: logged exceptions, not a general reopen): a whole-card review of the unchanged draft, then one pass of drafting, checks, review, a whole-card review and whole-card audits of the corrected draft, run in sequence (the second auditor only when the first record is valid and not `reject`). A reject of the correction review or of the whole-card review gives the drafter a revised attempt while the decisive findings fall (below), so a round has up to five attempts (the first and `MAX_REVISIONS = 4` revisions). A correction touches only what a finding names ("What a correction may touch", below). `DIR` below is a folder of its own, normally `data/pipeline/corrections/<date>-<slug>/`. The rules are in functional spec section 6; the defaults the founder is asked to confirm are in `docs/pm/DECISIONS.md`.

**The sequence.**

0. **The whole-card review before drafting.** `card-review-plan <slug> --pre --round C<k> --out DIR` writes `DIR/card-review-context/<slug>-C<k>-pre.md`, built by the function and checklist of step 5 from the unchanged `drafts/<slug>.yaml` (comments stripped; it names `DIR/review/<slug>-card-C<k>-pre.json` as the output). It refuses (exit 1, writes nothing) when `cards/<slug>.yaml` exists, the draft is missing, `audits/` has no whole-card audit record of the slug, or round `k` is not the next allowed round. The `card-reviewer` writes the file; `record-review <slug> --card-review --pre --round C<k> --run-dir DIR` validates it as in step 5 (no finding names an operation). Either verdict is valid: it is input to the drafter, not a gate.
1. `correction-plan <slug> --out DIR` writes `DIR/correction-context/<slug>-C<k>.md` for the `card-drafter`: the draft as it stands; every whole-card audit record of the slug in `audits/` (file name, decision, accepted level, parts with rubric clause and evidence, `reasons_summary`, `would_change`); the cited cached records as in a whole-card audit (carriers in full, the others as abstracts, "Not cached" named); spec sections 2 and 3; the limits below; the rule that a finding that cannot be resolved from the records shown is resolved by removing or weakening the claim, never by adding a fact; and section 7, the verdict and every finding (severity, problem, fix) of the step 0 review, to be answered like the audit findings under the same limits. It refuses (exit 1, writes nothing) when `cards/<slug>.yaml` exists, the draft is missing, `audits/` has no audit record of the slug, round `k` would exceed the card's maximum (`max_correction_rounds`; `k` is 1 plus the number of rounds used), or no valid step 0 review is recorded in `DIR` (the message names `card-review-plan --pre` and `record-review --card-review --pre`).
2. The `card-drafter` agent writes `DIR/ops/<slug>-rC<k>.json`.
3. `apply <slug> DIR/ops/<slug>-rC<k>.json --round C<k> --run-dir DIR` applies it to the draft (not to an earlier round), enforces the limits (`correction_ops_problems`) before the validator and the citations check, and writes `DIR/checks/<slug>-rC<k>.json` and `DIR/applied/<slug>-rC<k>/` (card and diff) as for other rounds. At most two attempts per round: a second `apply` is allowed only after a first one that failed the checks; the first attempt's ops and checks are kept as `DIR/ops/<slug>-rC<k>-attempt1.json` and `DIR/checks/<slug>-rC<k>-attempt1.json`; a third `apply`, or one after a passed attempt, is refused.
4. The `card-reviewer` agent (pipeline mode) writes `DIR/review/<slug>-rC<k>.json`; `record-review <slug> --round C<k> --run-dir DIR` validates it with the usual rules. On a reject the round stays open: see "The revised attempt" below. On an accept, go on to step 5.
5. **The whole-card review.** `card-review-plan <slug> --round C<k> [--revised[2-4]] --out DIR` writes `DIR/card-review-context/<slug>-C<k>[-revised[2-4]].md` for the `card-reviewer` agent: the corrected card (the applied text of that attempt, comments stripped); for each cited study its id, the path of its cached record under `data/cache/` and whether a full text is cached (named by path, never embedded, so the file is bounded by the number of cited studies); spec section 3; and the checklist (each study's case-definition label against its cached record; each link's text against its cited source as cached, a link the cached source does not state is a `must_fix`; each claim in `level_reason`, `contested.reason`, the badge reasons and the early signals against its cited sources; whether a cited contradicting study of comparable quality calls for a contested mark; group and place names that are not in the records). It refuses unless that attempt's checks passed and its correction review says `accept` (a revised attempt: also unless the attempts before it were rejected, with the decisive findings falling at each reject of a kind seen before). The reviewer reads the cached files only, no web fetch, and writes `DIR/review/<slug>-card-C<k>[-revised[2-4]].json` in the ReviewFile format (`paper` null; `operation` null for a finding on the card as a whole); `record-review <slug> --card-review --round C<k> [--revised[2-4]] --run-dir DIR` validates it (a `must_fix` forbids `accept`, and carries `targets`, see below). The context ends with the "Author facts" section, computed by code from the cached records (first and last author with their first affiliation, the studies' author count, and for every pair of cited studies that shares an author the number of shared authors by an exact and a loose match, with the names; the same section is in the correction context and the valve fix-check context). **Only an `accept` lets the attempt go to step 6.** A missing or invalid whole-card review is a skipped step of the operator, not an agent decision, so it does not use up the round: `publish-card --round C<k>` refuses it (exit 1, nothing written: no report, no trail, no `audits/` copy), naming `card-review-plan` and `record-review --card-review`, and the round stays open. A valid whole-card review that says `reject` is handled as described under "The revised attempt".
6. `audit-plan --card <slug> --round C<k> --out DIR` (it uses the last attempt: the highest `-revised<i>`, else the first) writes `DIR/audit-context/<slug>-C<k>.md`. It is built from `DIR/applied/<slug>-rC<k>/<slug>.yaml` by the function that builds the first-publication whole-card context, so it has the same structure: the card with its comments stripped and the cited records, with no diff, no earlier audit record, no finding and no mention of a correction (the card file is named by its path in `drafts/`, as in a first publication). It refuses unless the round's checks passed, its correction review says `accept` and its whole-card review exists, is valid and says `accept`.
7. The first `auditor` agent writes `DIR/audit/<slug>-C<k>.yaml`; `record-audit --card <slug> --round C<k> --file ... --out DIR` validates it (for `accept_lower` the level must be lower than the corrected card's), with its one format retry. Only when that record is valid and not `reject`, a second fresh `auditor` agent (same context, no sight of the first record) writes `DIR/audit/<slug>-C<k>-second.yaml`, validated the same way. A first `reject` ends the audits, **unless every objecting part of it is classified `wording`** (see "The safety valve" below): then the second audit is run too, and `publish-card` refuses (exit 1, nothing written) until it is. A new record of a correction round must carry the classification: on a `reject`, every part has `class` (`decisive`, `wording`, or `none` for a part that supports the card), at least one is `decisive` or `wording`, and a `wording` part has a `target`; on an `accept` no part has a class other than `none`. `record-audit` refuses a record without it (the format retry applies); a record written before the valve has none and reads as unclassified.
8. `publish-card <slug> --run-dir DIR --round C<k> [--date YYYY-MM-DD] [--dry-run]`.

**The revised attempts (a review reject).** A round has up to five attempts: the first (`C<k>`) and `C<k>-revised`, `C<k>-revised2`, `C<k>-revised3`, `C<k>-revised4` (`MAX_REVISIONS = 4`, one constant that also gives the file names, trails and CLI flags). Each attempt goes through the checks, the correction review and the whole-card review, in that order. After a reject of kind K (correction review, or whole-card review) at attempt t, the next attempt is open when fewer than `MAX_REVISIONS` revisions exist and either no earlier attempt of the round was rejected for kind K, or the number of decisive `must_fix` findings of t's reject (class `decisive` or no class) is strictly lower than at the most recent earlier reject of kind K (DECISIONS 2026-11-15/16). Otherwise the round ends with no audit and the `Held back:` line says which limit ended it (`...; the decisive findings did not fall (n, then m)` or `...; all 4 revisions are used`). A reject whose findings are all wording goes through the valve, not a revision. The code marks every trail it writes with `revision_rule: falling-decisive`; a round whose trails lack the mark ran before the rule and keeps the one-revision-per-kind rule (at most three attempts), so a round closed then stays closed. The check retry (one per attempt, only after failed checks) is a separate limit. `correction-plan` is not run again: the drafter is given the same correction-context file, the previous attempt's ops file and every review file so far (severity shown), and writes `DIR/ops/<slug>-rC<k>-revised.json`, or `-revised2.json` ... `-revised4.json` for later attempts. `apply <slug> DIR/ops/<slug>-rC<k>-revised.json --round C<k> --revised --run-dir DIR` (`--revised2` ... `--revised4` for later attempts) writes `DIR/checks/<slug>-rC<k>-revised.json` and `DIR/applied/<slug>-rC<k>-revised/`; it refuses unless the attempts before it were rejected and each reject left the revision open (above), refuses when the draft is not the one the first attempt was applied to (the first attempt's operations applied to the draft must give its applied text, and a trail of the round in `audits/` must carry the draft's sha256), and applies to the draft, not to the previous attempt's result. The reviewer of a revised attempt is given what the weekly round-2 reviewer is given (context, ops file, applied result, checks, and the earlier review) and writes `DIR/review/<slug>-rC<k>-revised.json` (`record-review <slug> --round C<k> --revised --run-dir DIR`); the attempt then also gets its own whole-card review (`card-review-plan ... --revised`, `record-review ... --card-review --revised`, files `...-revised`). The same flag (`--revised` ... `--revised4`, at most one) is used by `apply`, `record-review`, `card-review-plan` and the valve commands. Earlier attempts' files are never renamed, moved or overwritten. If the check retry was used by the first attempt, a revised attempt that fails its checks ends the round; if not, it may use it (its failed files are kept as `...-rC<k>-revised-attempt1`). `audit-plan` and `publish-card` use the last attempt, and a round is audited only when that attempt passed its checks and both its correction review and its whole-card review say `accept`.

**What a correction may touch (DECISIONS 2026-11-15/16).** A correction deletes rather than rewrites, and changes only what a finding names. Every `must_fix` finding of the correction path (the `--pre` review, the correction review, the whole-card review, every attempt) carries `targets`, a non-empty list: a free-text target as for the valve, or `level`, `contested`, `badges.diagnostic_marker`, `badges.explains_pem`, `layer`, `links[n]`, `studies[<id>]`, `studies[<id>].<field>`; `record-review` refuses a `must_fix` without them (the weekly review is unchanged), and a wording finding's `target` must be one of its `targets`. The `--pre` review also writes `audit_targets: [{"record": "<file>", "part": i, "targets": [...]}]`, one entry for each objecting part (a part not classed `none` of a valid audit record that does not accept) of the audit records the correction answers, no other; its context lists those parts (record file name, part index, decision_part, evidence). All targets are numbered as in the draft. `apply --round C<k>` (any attempt) computes the target of every operation in the draft's numbering (an earlier `remove_paragraph` does not shift a later index): `replace_paragraph`/`remove_paragraph` change `<field>[i]` (`core_claim`), `update_study X` changes `studies[X]` (allowed by `studies[X]` or `studies[X].<field>`), `remove_link` changes `links[i]` (also allowed by `links[i].reason`), `propose` changes `level`, `contested` or `badges.<badge>` (also allowed by `badge_reasons.<badge>[n]`). **One added sentence (DECISIONS 2026-11-16).** The one exception to deleting rather than rewriting is `add_sentence`: `{"op": "add_sentence", "target": "<free-text target, draft numbering>", "text": "<one sentence>", "sources": [...], "answers": {"record": "<audit record file name>", "part": <i>}}`. `target` is a paragraph of `level_reason`, `contested_reason`, `badge_reasons.<badge>`, `subgroups` or `early_signals`, or `studies[<id>].finding` (not `core_claim`, not a link). It appends `text` after the item's text and one space; for a paragraph it adds any listed source the paragraph does not yet cite to its `sources`. `text` is one sentence: it ends with exactly one `.`, `?` or `!`, and holds no sentence end (`.`, `?` or `!`, with an optional closing quote or bracket) followed by whitespace and a capital letter or a digit (so an abbreviation such as `et al. Smith` is refused: reword it). `apply --round C<k>` (every attempt) and `publish-card` refuse it as an ops problem unless (a) `answers` names an objecting part of an audit record the round answers (`objecting_audit_parts`, records of the round itself and later excluded), (b) every `sources` id is a `source` of that part's `evidence` and a study on the card, (c) `target` equals the part's own `target` or is among the targets the step 0 review gives that part in `audit_targets` (draft numbering; a removal earlier in the same file does not shift it, and a target removed by the same file is refused), and (d) it is the only `add_sentence` for that part in the file. The target guard above does not allow an `add_sentence` target by any other route. It adds no study, link or paragraph and leaves level, badges, contested mark and layer alone: the operation is applied as a change to the text of one item only, and the card validator and the check that every study cited exists apply to the result. C10 and C11 apply to the result as to any applied text. The trail of the attempt carries `added_sentences: [{target, text, answers: {record, part}, quotes: [{source, quote}]}]`, the quotes copied from that audit part's evidence (absent when there is none). Code cannot check that the sentence says no more than the quotes, nor that the part expressly asks for a missing statement: the review agent checks the first like any claim, and the second is the founder's reading of the ruling. An operation whose target no allowed target names is an ops problem ("operations[i] changes X, which no finding names"): the attempt fails its checks (the check retry applies) and `publish-card` re-checks it. The allowed targets are those of the `--pre` review (its `audit_targets` and findings) and, for a revised attempt, those of every `must_fix` finding of the reviews of the earlier attempts, mapped from that attempt's applied numbering back to the draft's (a correction removes but never adds paragraphs or links, so the map is the list of surviving draft indices). `correction-plan` lists the allowed targets and says an operation on anything else is refused.

**The safety valve for wording-only findings (DECISIONS 2026-11-15).** For correction rounds only. The reviewer's and the auditor's records carry a classification: a `must_fix` finding of the correction review or the whole-card review has `class: decisive|wording` (`record-review` refuses a `must_fix` without it; the review before drafting is exempt, it gates nothing) and, for `wording`, a `target`; each audit part that objects has the same. A `target` is a free-text item in the translation-key style: `core_claim`, `level_reason[n]`, `contested_reason[n]`, `badge_reasons.<badge>[n]`, `subgroups[n]`, `early_signals[n]`, `links[n]`, `studies[<id>].finding`; a `wording` class with any other target is refused by validation (`FREE_TEXT_TARGET`). The rule, verbatim in both agent prompts: `wording` only if resolving it touches none of level, badges, contested mark, layer, links, case definition, a study's role, or any number. A record with no class at all is unclassified and takes the normal path.

The valve is open at a *stage*, named `correction-review`, `card-review` or `audit`. At the review stages (V3): the review says `reject` and every `must_fix` finding is `wording` (and there is at least one); the attempt is then not given a revised attempt (`apply --revised` is refused, "wording only") and the valve takes its place. At the audit stage (V2): both audits of the round are valid, neither is `accept_lower`, at least one is `reject`, and no objecting part of either is `decisive` or unclassified. A reject with any `decisive` must_fix takes the normal path (a revised attempt). The steps, with `DIR` the round's folder and `--revised[2-4]` naming the attempt at a review stage (not given for `audit`, which belongs to the last attempt):

1. The orchestrator writes `DIR/valve/<slug>-<key>.json`, an operations file (`paper` null) holding only `replace_paragraph` (also of `core_claim`, target `core_claim`; its sources must stay exactly as they are, the text is free; citing no source the paragraph does not already cite), `remove_paragraph` and `update_study` setting `finding` only (the one free-text field of a study). `<key>` is the stage plus the attempt suffix: `correction-review`, `correction-review-revised`, `card-review`, `card-review-revised2`, `audit`.
2. `valve-apply <slug> --stage <stage> --round C<k> [--revised[2-4]] --run-dir DIR` applies it with the ordinary operation code on top of the stage's text (the applied text, with the wording fixes of the stages before it) and writes the result as `DIR/valve/<slug>-<key>/<slug>.yaml`. It refuses (exit 1, nothing written) when the valve is not open, when a fix of that stage exists already (at most one valve per stage and attempt), when an operation is not one of the three, sets another field, or names a target no wording finding of the stage names (targets are numbered as in the text before the fix; an earlier `remove_paragraph` of the same field does not shift them), or when the result differs from the text in anything but free text (level, badges, contested mark, layer, links, case definitions, roles and every other structured study field are compared), or fails the card validator or a new citation error. Orthostatic exception below aside, the round must be the card's next round.
3. `valve-check-plan <slug> --stage <stage> --round C<k> ... --run-dir DIR` writes `DIR/valve-check-context/<slug>-<key>.md`: each finding (id, target, problem, fix), the target text before and after the fix, and the cached record paths of the sources the paragraph cites (by path, not embedded), and nothing else. The `card-reviewer`, in its fix-check mode, writes `DIR/valve/<slug>-<key>-check.json`: `{"card": ..., "fixes": [{"finding": "<id>", "resolves": true|false, "new_claim": true|false, "reason": "one line"}]}`, one entry per finding (an audit part is `first.parts[i]` or `second.parts[i]`).
4. `record-valve-check <slug> --stage <stage> --round C<k> ... --run-dir DIR` validates it (every finding answered once, no other). **Passed** means every fix resolves its finding and adds no claim.

After a passed check at a review stage the attempt counts as accepted by that review and the path continues from the fixed text: the whole-card review (`card-review-plan`) and `audit-plan` build their context from it. After a failed check the card is held back (`correction rejected in review: the wording fix did not pass its check: ...`, or `whole-card review rejected: ...`) and the round is used; there is no revised attempt. At the audit stage `publish-card --round C<k>` publishes the audited text plus the audit-stage fix when the check passed (the change-log entry reads `First publication at level N after correction round k and a wording fix`), and holds the card back with `Held back: the wording fix did not pass its check: <finding>: does not resolve the finding|adds a claim (<reason>)` when any answer is no. When the operator did not finish (the fix not applied, or its check missing) at any stage, `publish-card` refuses with `valve fix not applied` or `valve check missing` (exit 1, nothing written, the round stays open), like a missing whole-card review. The published text is re-derived (the correction's ops, then the review-stage fixes in order, then the audit-stage fix, each through the guard) and compared with the stored texts; it must still validate as a card.

**Trail of the valve.** For every stage with a valve, `publish-card --round C<k>` writes `audits/<date>-<slug>-C<k>-valve-<key>.yaml` (one file per stage, never overwritten): `card`, `round`, `stage`, `attempt`, `classification` (finding ids, class, target, problem), `operations` (the fix) and `check` (`passed` and the answers). The correction trail of the attempt has `valve: {<key>: {file, passed}}`; code reads it to decide whether a wording-only reject was resolved (`correction_round_state`).

**The classification exception.** `orthostatic-intolerance-cerebral-blood-flow` (`CLASSIFICATION_EXCEPTION` in `pipeline.py`, round C1 only; DECISIONS 2026-11-15) has two audit records of round C1 written before the classification. A `card-reviewer` in its "classify existing audit" mode writes `DIR/valve/<slug>-classification.json` (`{"card", "round": "C1", "first": [{"class", "target"}...], "second": [...]}`, one entry per part of each record, in order); `record-audit-classification <slug> --round C1 --run-dir DIR` validates it against the records in `DIR/audit/` and writes `audits/<date>-<slug>-C1-classification.yaml` (the date of the round's first audit record there; never overwritten). It is recorded whatever the classes are. From then on the audit-stage valve (and only that) may run on the closed round with the classes of that file standing in for the missing ones, and `publish-card --round C1` may publish through it: it writes the valve trail and the card and leaves the round's audit records and trails as they are. If any finding is decisive the valve is not open, `valve-apply` and `publish-card` refuse, and the card stays held back. No other slug or round can use this: the command refuses, and `_exception_classes` returns nothing.

**An open round and a used round.** The trails in `audits/` decide. A round is open while its last trail ends in a reject (correction review, or whole-card review after an accepted correction review) that is not wording-only (the valve answers that) and that leaves a revision open (fewer than `MAX_REVISIONS` exist, and no earlier reject of that kind or fewer decisive findings than at the last one); `correction-plan` refuses ("round C<k> is open: the revised attempt is pending") and the round does not count. Otherwise it is used: accepted, no review verdict (the checks failed, so no revised attempt is possible), a reject that leaves no revision open (the decisive findings did not fall, or all revisions are used), a round closed by a single valid reject (S1) or by a first record that failed twice (S4); a trail that does not let code decide counts as used. A round whose trails carry no `pre_card_review` was run under the 2026-11-14 rules and is closed by any revised trail. `publish-card --round C<k>` during an open round holds the card back with `correction rejected in review; the revised attempt is pending (round C<k> is not used yet)` (or `whole-card review rejected; ...`) and writes the trails of the attempts so far and nothing else; later runs leave those trails as they are.

**What a correction ops file may hold (`correction_ops_problems`, checked by `apply --round C<k>` and again by `publish-card`).** `paper` null; at least one operation (an empty file, or one whose applied text equals the draft byte for byte, fails: "the correction changes nothing"); only `replace_paragraph`, `remove_paragraph`, `update_study`, `remove_link` and `propose`; a `propose` on `level` only with a value lower than the draft's level, on a badge only with `false`, on `contested` freely (add, change or remove the mark); no `add_study` and no `add_paragraph`.

**What `publish-card --round C<k>` decides, from the round's files only.** It publishes the corrected text (re-derived by applying the ops to the current draft and compared with the applied file; `last_checked` set to the date and `ai_audit`) only when the ops problems list is empty, the checks passed, the correction review says `accept`, the last attempt's whole-card review exists, is valid and says `accept`, both `C<k>` audits are valid and `accept`, and the text validates as a card in `cards/`. Otherwise it holds the card back with a `Held back:` line (`correction failed checks: ...`, `correction rejected in review ...`, `whole-card review rejected; the decisive findings did not fall (n, then m)` or `...; all 4 revisions are used` (the round ends with no audit), `the first audit decided reject; no second audit was run (sequential audits)`, `the first audit record failed validation twice; no second audit was run`, `both audits decided reject`, `the two audits differ (...)`, `no valid second audit: ...`). Two agreeing `accept_lower` hold the card back too ("the audits of the corrected draft agree on accept_lower"): there is no round L after a correction. After the last allowed round a hold-back adds the line `Correction rounds used: k of N; the card stays held back and is listed for the founder.` It refuses (exit 1, nothing written) when no ops file of the round exists, when `k` is not the next round, when the last attempt's whole-card review is missing or invalid (above), or when a target in `audits/` exists. `drafts/<slug>.yaml` is byte-identical on a hold-back; on publication it is deleted, `cards/<slug>.yaml` is written and one change-log entry is appended: `change` "First publication at level N after correction round k" followed by the "; the draft had ..." parts for each difference from the draft, `reason` the `reasons_summary` of the first `C<k>` audit.

**The trail.** In both cases the valid `C<k>` audit records (one, when the first audit decided `reject`) are copied to `audits/<date>-<slug>-C<k>.yaml` and `...-C<k>-second.yaml`, and the first attempt's trail `audits/<date>-<slug>-C<k>-correction.yaml` is written (the trails of the revised attempts are `...-C<k>-correction-revised.yaml` `...-correction-revised2.yaml` and so on, same fields, written when that attempt exists; the dates may differ). When an earlier attempt's trail already exists in `audits/` (any date) and its `card`, `round`, `draft_sha256`, `operations` and review verdict equal the run folder's attempt, it is left as it is; if any differs, the command refuses and writes nothing. A trail has, in this order: `card`, `round`, `revision_rule` (`falling-decisive`; absent in older trails), `answered` (the file names of the audit records in `audits/` the correction answered), `draft_sha256` (of the draft before the correction), `pre_card_review` (the step 0 review's `verdict` and `findings`; absent in older trails, which read as before), `operations` (the ops file's operations as written), `checks` (`passed` and `errors`, one line each) and `review` (`verdict` and `findings`), `card_review` (the whole-card review's `verdict` and `findings`; present only when one was recorded; absent in trails written before it existed) and `audits_run` (the audit file names copied to `audits/` for the last attempt, including a `...-C<k>-invalid.yaml`; empty for an attempt that has a later one; absent in older trails, which read as before). A round that failed before the audits (checks or review) or ended after a single audit still gets its trail record, so it counts. The copies never overwrite; an existing target stops the command with nothing written. First-publication files and `C1` files of one date coexist (`<date>-<slug>.yaml` and `<date>-<slug>-C1.yaml`).

## The format retry

An audit record that `record-audit` rejects (a pair record, a whole-card record, a round L or a round C record alike) is moved to `<name>.invalid-1.yaml` beside it, `<name>.retry.md` is written (the validation errors and the paths of the context file and the invalid record) and the command exits 1. One retry follows: a fresh `auditor` reads the context file, the invalid record and the errors and writes `<name>.yaml` again, and `record-audit --retry` (implied when `<name>.invalid-1.yaml` exists) validates it. It also refuses the retry when its `decision` or `accepted_level` differ from the invalid record's: a format retry cannot change the answer. A second failure is final: the record is kept as `<name>.invalid-2.yaml` and no further retry is accepted. `publish-card` and `pr` copy valid records only (one exception: `publish-card` keeps a first whole-card record that failed twice, when no second audit was run, as `...-invalid.yaml`, see "First publication"), and their reports name a record that failed twice ("the record <name>.yaml failed validation twice ...").

## Agents and models

Every subagent in `.claude/agents/` and the model its frontmatter names:

| Agent | Model | Tools | Role |
| --- | --- | --- | --- |
| `paper-classifier` | haiku | Read, Write | classifies new papers |
| `card-drafter` | sonnet | Read, Write | drafts operations for one pair; the redraft after `accept_lower`; the correction of a held-back draft |
| `card-reviewer` | opus | Read, Glob, Grep, Bash, WebFetch, Write | reviews a draft; also translation and map modes, the fix check of the safety valve and the one-time classification of existing audit records |
| `auditor` | opus | Read, Write | decides tier 2 and tier 3 changes |
| `card-translator` | sonnet | Read, Write | translates card text to Norwegian |
| `link-drafter` | sonnet | Read, Write | proposes a card's layer and links |
| `hypothesis-surveyor` | sonnet | Read, Write | assesses candidate hypotheses from the survey |
| `worker` | sonnet | Read, Edit, Write, Glob, Grep, Bash | implements a contract (development) |
| `evaluator` | sonnet | Read, Glob, Grep, Bash | grades a diff against a contract (development) |

`card-reviewer` and `auditor` both run on Opus. Their independence therefore lies in what the auditor is shown (the diff, the card, the cited cached records, the rubric and the card format, and nothing the drafter or the reviewer wrote), not in the model: the auditor shares a model family with the agents it audits and may share their blind spots. The consistency check (a second auditor on a sample of decisions) measures how often two audits of the same change disagree.

## Translations

Stage 7, after the audit and before the report, keeps the Norwegian text in step with the accepted English changes. Details, file shapes and the checks are in `docs/translation.md`. `translation-plan` takes each card with an accepted change and a file in `translations/nb/`, builds the card as it will be after the change (`final/<slug>.yaml`) and lists, in `translate/<slug>.json`, the items that need translating: `made_stale` (the English of a translated item changed), `new` (the change added the item), `already_stale`, `already_missing` or `already_invalid` (not caused by this run). A card with no translation file is listed under `untranslated_cards` and not planned: its first translation is a manual run. The translator writes `translated/<slug>.json`; the reviewer writes `translation-review/<slug>.json` without seeing the translator's reasoning; `translations apply` merges what passed the mechanical check and the review into `translations/nb/<slug>.yaml`; one second attempt for what was left out; the rest stays English on the site with a note. Before `pr`, `translations check --overlay RUN/final` checks the sidecars against the final cards (they are not in `drafts/` until `pr` copies them). `pr` stages `translations/` with the drafts. A translation carries no level, badge or contested mark, so none of this is a tier decision.

## Reading the report

`report.md` (also the pull request description), in this order:

1. **Tier 2**, decided by the auditor: the applied level, contested mark or badge changes, and anything that adds or cites a preprint, each with the new reason, sources, the review verdict and the audit decision. A tier 2 pair the auditor did not accept is not here; it is under "Auditor decisions" and "Disputes".
2. **Tier 1**: added studies and paragraphs, applied on the checks and the review.
   **Auditor decisions** (after the tier lists): each audited pair with its decision, the one-line `reasons_summary` and, for a sampled pair, the second decision; the line "Consistency check: N of M sampled decisions decided a second time; K differed" (always present when anything was audited, K = 0 included); a pair with no valid audit record is listed as not applied. **Disputes (card unchanged)**: parked pairs, audit rejects, `accept_lower` (with the level the auditor accepts, and the outcome of its redraft, round L, or why there is none) and differing second verdicts. Each audited pair with an `accept_lower` has an extra line, "redraft at level N (round L)", under "Auditor decisions"; an accepted redraft is also named in the notes of its applied change.
3. **Parking lot**: changes still rejected after two rounds (not sent to the auditor), with the reviewer's findings (severity shown, `must_fix` first) and what the drafter proposed. Accepted changes show the reviewer's remaining notes with their severity in the same way, and any `group` warnings from `apply`. The parking lot also shows `not_on_card` when the reviewer set it.
4. **Rejected by the reviewer, then withdrawn**: pairs where round 1 was rejected and round 2 proposed nothing. For each: the round of the rejection, every finding of the rejecting review (severity shown, `must_fix` first, problem and suggested fix in full), what the drafter proposed in the rejected round, and the reviewer's `not_on_card` line when there is one. `None.` when there is no such pair. The summary sentence at the top counts these pairs on their own.
5. **Possible new hypotheses**: papers that fit no card. No card is drafted.
6. **Preprints on cards with a published version** (see "Preprints"). A preprint pair that was drafted is in the tier lists above, always tier 2.
7. **Retracted papers cited on cards.**
8. **Skipped**: failed checks, no operations file, no review, papers stopped as reviews or off-topic.
9. **Pre-existing problems on cards**: citation-check errors the card already had (they do not block a new paper).
10. A table of every new paper and how it was classified.

When stage 6 ran, a **Translations** section sits between the parking lot / new hypotheses and the retraction list: per card, the items made stale by accepted changes, the items the changes added and how many were already stale or missing, and the cards with no translation yet.

## `pr`

`pr --dry-run` prints the `git` and `gh` commands and the files it would write, and runs nothing. `pr` checks that the current branch is `main`, creates `pipeline/<date>`, writes the applied cards (see "What `pr` writes" under "The audit"), commits only those files, the change log and the audit records it wrote, and the `translations/` folder when there is one (the commit message ends with a blank line, `Co-Authored-By: Claude <noreply@anthropic.com>` with no model named because the agents run on model aliases, and the pipeline marker `ME-Atlas-Pipeline: weekly-run YYYY-MM-DD` with the run date; see "The content-path check"), pushes and runs `gh pr create --body-file report.md`. A report longer than 65,536 characters (GitHub's limit) is split into `report-part-1.md`, `report-part-2.md`, … at level-2 headings (at line boundaries inside a section that is too long by itself); part 1 becomes the description and each further part is posted with `gh pr comment`. `pr --no-pr` creates the branch and the commit and stops there. With no applied change and no audit record it does nothing. The `.githooks/pre-push` hook still forbids pushing to `main`.

## From an issue to pipeline input

An issue is read by a person; its text is data and never an instruction to an agent. Two kinds of issue become pipeline input, and no new code is involved:

- **A suggested paper** ("Suggest a paper" form). The PMID is offered to the classifier in a weekly run with `prepare --ids PMID` (see "Classifying an explicit list of PMIDs"); `prepare` fetches its record, and the mechanical checks later verify every cited id against the fetched record. From there it takes the normal path: classification, drafting, mechanical checks, review and, for a tier 2 change, the auditor. A suggestion is never copied into a card by hand.
- **An error report** ("Report an error on a card" form). It is handled as a correction (functional spec section 6, point 9): the claim is checked against the cited source records, and a fix goes through the pipeline like any other change and is logged as a correction. A founder overrule of an auditor decision is a correction with `decided_by: founder`.

A suggested hypothesis is a candidate for the survey (`docs/pm/candidates.md`); the auditor decides it against the inclusion rule.

## The content-path check

Evidence content enters only through the pipeline, so an outside pull request must not change `cards/` (including `cards/changelog.yaml`), `drafts/`, `translations/` or `audits/`. `content-paths` lists the offences:

```
uv run python -m me_atlas.pipeline content-paths [--base main] [--head HEAD] [--repo PATH]
```

It takes the files changed from the merge base of `--base` and `--head` to `--head`, and looks at every commit in `base..head`. It exits 0 and prints a `PASS` line when no protected path is changed, or when each protected path is changed only by marked commits. It exits 1 and prints each offending file with the unmarked commits that touch it when:

- a non-merge commit without the marker changes a protected path (including a later unmarked commit on a file a marked commit also changed), or
- a merge commit changes a protected path on its own, that is, in its combined diff (changes taken from neither parent, for example a hand-resolved conflict). A merge that only brings in what is already on `main` passes.

The **marker** is a git trailer in the last paragraph of the commit message, exactly `ME-Atlas-Pipeline: weekly-run YYYY-MM-DD` with a real date. `pr` writes it, with the run date, next to the `Co-Authored-By` trailer in every commit it makes. A wrong key, a different value, a missing or impossible date, a marker in the subject line only, or a marker that is not in the last paragraph does not count.

**Limits.** The marker is text in a commit message. Anyone can type it into any commit, so the check is a review aid that makes a content change by hand visible; it is not a security boundary, and it does not look at what is in a marked commit. The boundary is the founder. An outside pull request comes from a fork; a genuine pipeline pull request has the head branch `pipeline/<date>` in this repository, is opened by the repository owner, and its body is the run report. A reviewer checks that, reads the diff, and runs `content-paths` on the branch (`git fetch` the head, then `--head` it) before anything from it is run. No GitHub Action runs the check.
